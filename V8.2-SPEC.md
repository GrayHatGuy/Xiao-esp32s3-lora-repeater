## 1. Purpose & scope

Bring the RX-priority routing redesign (route queue + CAD listen-before-talk +
content-hash dedup + airtime throttle) from the unreleased 4-radio
`T_LORA_QUAD_ROUTE` branch onto the **shipping 2-radio dual-SX1262 design**
(`main`, v8.1), and add a **source-identity preservation layer** so a bridged
repeat carries (or reconstructs) the original sender's node ID and protocol
instead of appearing to come from the bridge.

**In scope:** everything host-side that touches the SX1262 path (R1/R2).
**Out of scope (explicitly):** all LR1121/co-processor material — `UartLink`,
`LinkProtocol`, `RemoteRadio`, `WioLR1121`, `RadioProfile`, the
`coproc-tlora-dual/` firmware, BridgeConfig schema v6, the 4-radio portal UI,
and the routing matrix. LR1121 functionality is unproven (RX deficit
investigation ongoing); none of it lands in v8.2. BridgeConfig stays at
**schema v4 — no NVS migration**, so an upgraded v8.1 device keeps its config.

**Versioning note:** a `v9.0` tag exists but lives on the `lr1121-phase1`
branch lineage (Phase-1 LR1121 bring-up), not on `main`. `main`'s latest
release tag is `v8.1`, so `v8.2` is the correct next tag for this line.

## 4. Challenge analysis — why identity is lost, and what each protocol allows

The redesign strips the `[MT !id name]`/`[MC]` marker (clean far-side bodies),
so a bridged repeat is emitted under the **bridge's own identity** (MT) or
**no identity at all** (MC). What each side structurally offers:

- **Meshtastic** (decoder `MeshDecoderDebug.h:193-198`, encoder
  `MeshEncoderDebug.h:116-200`): the 16-byte cleartext header carries
  `src` (4 B) and `packet_id` (4 B). The encoder **already takes `srcNodeId`
  as a parameter**, and `encodeMeshtasticNodeInfo()` can mint a NodeInfo for
  **any** identity. The AES-CTR nonce is built from `packet_id`+`src` only, so
  preserving those two fields keeps ciphertext valid across header edits, and
  re-encrypting the same Data payload for a different channel key is possible
  without touching the protobuf. Native MT nodes dedup floods on (src,
  packet_id) and relayers decrement `hop_limit` (flags byte layout per the
  captured-packet analysis at `MeshEncoderDebug.h:167-171`; relay semantics to
  be **cited from Meshtastic firmware docs during implementation and proven at
  bench** — they were argued, not cited, in the branch review).
- **MeshCore GRP_TXT** (encoder `MeshEncoderDebug.h:44-108`): plaintext is
  `[ts:4][flags:1][body…\0]` — **no sender-identity field exists in the
  packet**. Identity rides *inside the body by convention*: real MeshCore
  clients send `"<name>: <text>"` (this is why v8.1's MC marker stayed bare —
  `main.cpp` comment "MC packets already carry the sender's name inline").
  So on the MC side, attribution can only ever be body-level text.

**Conclusion:** same-protocol identity preservation can be *exact* (carry the
original header). Cross-protocol preservation must be *reconstructed*: a
**deterministic virtual MT node** per MC sender (MC→MT), and a **name-prefix
body convention** (MT→MC). That is the design below.

## 5. Identity-preservation layer (the v8.2 feature)

Master switch `BRIDGE_IDENTITY_PRESERVE` (default **1**; `0` reproduces the
branch's clean-body/bridge-id behavior exactly).

### 5.1 Same protocol, same channel (name+key match, different frequency) — **transparent raw repeat**
The cross-frequency relay the freq-aware guard (A4) unlocks.

- **MT→MT:** re-transmit the **original bytes**, modifying only:
  `hop_limit` (flags[2:0]) decremented — packet with `hop_limit == 0` is
  **not** repeated; `relay_node` (byte 15) set to the bridge ID's low byte.
  `src`/`packet_id`/ciphertext untouched ⇒ far side sees the **original
  sender natively** — including **position, telemetry, and NodeInfo packets
  passed through in full fidelity** (no text-ification), and native (src,pid)
  dedup works. Packets with `src == bridge id` are skipped (self-echo).
  Only packets whose `channel_hash` matches the configured channel are
  repeated (conservative; "promiscuous repeat" noted as future option).
- **MC→MC:** re-transmit the original bytes **unchanged** (header, path, MAC,
  ciphertext). The body's native `"name: text"` arrives intact ⇒ identity
  preserved. *Open point:* a native MC repeater appends its hash to `path`;
  whether to mimic that needs a MeshCore-source citation — v8.2 ships
  unchanged-bytes repeat and records the question (§10-Q5).

### 5.2 Same protocol, different channels (different key) — **re-encrypt, preserve header**
- **MT→MT:** decrypt the Data payload with the source channel key (nonce =
  original pid+src), re-encrypt with the destination key, set the destination
  `channel_hash`, keep `src` and `packet_id`, decrement `hop_limit`.
  Identity exact; payload fidelity full (any portnum). New small helper in
  `MeshEncoderDebug.h` ("trans-crypt"); existing callers unchanged.
- **MC→MC:** decode (we already do), re-encode GRP_TXT with the destination
  key preserving `ts` and the body verbatim — `"name: text"` carries identity.

### 5.3 Cross-protocol MC→MT — **virtual node mapping**
- Parse the MC body's leading `"<name>: "` (1–40 printable chars, no ':').
- `virtualId = FNV-1a32("MC|" + name)`; re-hash on collision with reserved
  values (`0x00000000–0x000000FF`, `0xFFFFFFFF`) or the bridge's own ID.
  (Deterministic ⇒ the same MC sender maps to the same MT node across reboots
  and even across multiple bridges. 32-bit collision with a real node is
  possible but negligible at mesh scale — documented residual risk.)
- Emit the MT text with `src = virtualId` and the **name stripped from the
  body** (identity moved from text into the header where MT wants it).
- **`VirtualNodeMap`** (new, RAM-only, 32-entry LRU): name → virtualId +
  last-NodeInfo time. On first sighting and every
  `BRIDGE_VIRT_NODEINFO_PERIOD_MS` (default 15 min, only while active),
  enqueue a synthetic NodeInfo: `id="!<hex>"`,
  `long_name="<name> @MC"`, `short_name=` first 4 chars — so MT clients
  display the message *from "Alice @MC"*, not from the bridge.
- **No name parsed** ⇒ fall back to today's behavior (bridge identity, clean
  body). (§10-Q3 offers a per-channel catch-all virtual node instead.)
- Trust note: MC group identity is body text — anyone on the channel can claim
  any name. Virtual nodes are **display-level attribution at the same trust
  level as MC group chat itself**, stated plainly in README.

### 5.4 Cross-protocol MT→MC — **name-prefix convention**
- Resolve the MT `src` via NodeDB (short name; fallback `"!<8hex>"` — the
  32-bit origin ID stays recoverable in that form).
- Emit body `"<name>@MT: <text>"` (with `BRIDGE_TAG_ORIGIN_PROTO=0`:
  `"<name>: <text>"`, indistinguishable from a native MC sender).
- This is the only channel MC offers (no header identity field); it is
  attribution, not authentication.

### 5.5 Provenance summary ("nodeID/protocol known after repeat")
| Path | Node ID after repeat | Protocol provenance |
|------|----------------------|---------------------|
| MT→MT | exact (native header) | implicit (same protocol) |
| MC→MC | exact (native body/name + path) | implicit |
| MC→MT | deterministic virtual MT node per sender name | `@MC` suffix in NodeInfo long_name |
| MT→MC | name (+`!hexid` fallback) in body prefix | `@MT` suffix in body prefix |

## 6. Dedup / loop-safety interplay (analysis)

The DedupCache contract — record on RX *and* on every emission, drop on hash
match — is preserved under every §5 path:

| Path | Ingest records | Emission records | Echo of our TX hashes as | Result |
|------|----------------|------------------|--------------------------|--------|
| Text re-encode (today) | h(body, srcId) | h(body, dstSrcId) | emission hash | drop ✓ |
| MT raw repeat | h_raw = FNV1a(src‖pid) | (same as ingest) | h_raw (src/pid unchanged; mutable bytes flags/next/relay excluded from hash) | drop ✓ |
| MC raw repeat | h_raw = FNV1a(mac[2]‖ciphertext) | (same) | invariant even if a native repeater extends `path` | drop ✓ |
| MT→MT trans-crypt | h_raw(src‖pid) | h_raw(src‖pid) (unchanged) | same | drop ✓ |
| MC→MT virtual | h(fullBody, 0) | h(strippedBody, virtualId) | emission hash | drop ✓ |
| MT→MC prefixed | h(body, mtSrc) | h(prefixedBody, 0) | emission hash | drop ✓ |

The accepted MeshCore limitation (content-only dedup: two different MC senders
sending identical text inside the TTL lose the second bridged copy) is
**improved** when a name is parsed — the name participates via the body — and
unchanged otherwise.

## 13. Serial debug logging schema (v8.2) — owner Q1

**Decision:** adopt the owner's field set and extend it; replace the ad-hoc
`[%8lu ms][%s ...]` prose lines with a **single greppable, tagged `key=val`
line per event**, and ship a **dedicated log mutex** (separate from `spiMutex`)
so a line emits atomically across both cores. The heavy hex/protobuf decoder
dump (`MeshDecoderDebug::print`) stays its own multi-line block, preceded by an
`evt=RX` header so a parser can still anchor it.

**Why split the owner's one line into a few events:** the pipeline decodes +
dedups ONCE (`ingestAndFanout`, one `DedupCache::seenAndRecord`), then fans out
to up to N−1 destinations, each of which encodes → records-emit-hash → pushes,
after which a *separate* radio task (possibly on the other core) pops → CADs →
transmits → throttles. One line can't honestly carry all of that, so a small
enumerated `evt` tag set is used. It is a strict **superset** of the owner's
intent: "radio-emitted-or-drop" = `evt` + a `drop=` token; "hash ingested" /
"hash emitted" = `hin=` / `hout=` on the right events.

**Format:** every line starts `ts=<ms> evt=<TAG> radio=<R1|R2>` then only the
keys valid at that stage. `evt` ∈ {`RX`, `DEDUP_PASS`, `DROP`, `QUEUE`, `CAD`,
`TX_START`, `TX_DONE`, `THROTTLE`, `NODEDB`, `NODEINFO`}.

| Key | Stage | Source (ported `main.cpp`) | Notes |
|-----|-------|----------------------------|-------|
| `ts` | all | `millis()` | leading key, always first |
| `evt` | all | synthesized | the parseable event tag |
| `radio` | all | `kTag[i]` | RX radio for ingest; owning radio for TX-side |
| `proto` | RX | `g_chan[i].protocol` | `MC`/`MT`/`RNS` — disambiguates the id fields |
| `rssi`,`snr` | RX | `read(buf,len,&rssi,&snr)` | **added** — the key weak-RX bench fields the owner's list omitted |
| `len` | RX/TX | RX `len`; emitted `outLen` | RX truncation / airtime input |
| `nodeid` | RX | `buf[4..7]` (MT, `len≥8`) | owner's "nodeid"; **MT-only**, else `-` |
| `hin` | DEDUP | `DedupCache::hash(body,len,srcId)` | owner's "hash ingested"; logged on PASS and on `drop=loop-dup` |
| `drop` | DROP | enumerated branch | `loop-dup`/`rns-dup`/`self-echo`/`encode-fail`/`queue-full`/`frag-overflow`/`cad-busy`/`tx-startfail`/`tx-timeout` — a **token**, not prose, so loss is grep/awk-histogrammable |
| `dst` | QUEUE/TX | dest index `j`/`destIdx` | owner's "radio emitted"; without it a fan-out leg is unattributable |
| `virtualid` | IDENTITY | `dstSrcId` stamped on the re-encode | owner's "virtualid"; **MT-only** (0/`-` for MC by design) |
| `hout` | QUEUE | `DedupCache::hash(body,len,dstSrcId)` recorded pre-push | owner's "hash emitted"; lets a `loop-dup` be matched offline to our prior emit |
| `qdepth`,`qdropped` | QUEUE | `RouteQueue::count()`/`dropped()` | **added** — surfaces stale-age/overflow loss that is otherwise silent (one-line getters if not yet public) |
| `cad`,`backoff` | CAD | `scanChannel()`, `g_txBackoffUntil[i]` | **added** — channel-contention vs TX failure |
| `air`,`gap`,`nexttx` | THROTTLE | `estimateAirtimeMs()`, `g_nextTxAllowedMs[i]` | **added** — a duty-cycle hold otherwise looks like a hang |
| `frag`,`seq` | QUEUE | RNS `idx/total`, `crc16` low byte | **added** (RNS only) — ties fragments together |
| `ni_id`/`ni_short`/`ni_long`, `selfid`/`selfname` | NODEDB/NODEINFO | `extractMeshtasticNodeInfo`→`NodeDB::upsert`; `BridgeConfig::mt*` | the MC→MT virtual-node + synthetic-NodeInfo trail (§5.3) |

Re-scope note: `nodeid` and `virtualid` are populated only for Meshtastic
(`srcId` parsed only when MT & `len≥8`; `dstSrcId` is deliberately 0 for
MeshCore). They are emitted as `-` otherwise so a logged `0` is never mistaken
for "sender id zero."

## 14. LoRaWAN (LoRa sync 0x34) — staging decision + design — owner Q2

**DECISION (locked 2026-06-13): deferred wholesale to v8.3 — no LoRaWAN code in
v8.2, not even the enum/constant seam.** This section is the v8.3 design of
record. The research below shows LoRaWAN is **not a smaller version of the
existing bridge** — bidirectional *content* bridging is architecturally
precluded, not merely deferred. So the future feature is a **capture-only RX
metadata tap**, not an MC/MT-style content bridge.

### 14.1 Why LoRaWAN content bridging is precluded (verified against LoRaWAN L2 1.0.x/1.1 + Semtech)
The existing bridge works because MeshCore (public channel) and Meshtastic
(default-key channel) both expose **group/broadcast text under a shared or
well-known key** — so the bridge can decrypt one side and re-encrypt for the
other. LoRaWAN breaks every premise of that model:
- **No group/broadcast/well-known key.** `FRMPayload` is AES-CTR encrypted
  under a **per-device `AppSKey`**; the 4-byte MIC is AES-CMAC under a per-device
  network key. A bridge without each device's provisioned session keys reads
  **zero** payload bytes. (Confirmed: even a real LoRaWAN *gateway* — the
  privileged node — forwards the raw PHYPayload and never decrypts; decryption
  happens only at the Network/Application server.)
- **Star topology, not a peer text mesh.** Frames are addressed to a network
  server via `DevAddr`, not to a human-readable channel. There is no "post to a
  public channel" primitive to map an inbound MC/MT message onto.
- **TX is undefined for the general case.** Emitting a frame any device accepts
  needs that device's `DevAddr` + `AppSKey` + network key + the correct next
  monotonic `FCnt` + correct uplink/downlink `Dir` + (for a Class A device) a
  real-time RX1/RX2 downlink window right after *it* transmits — i.e. you must
  *be* its network server. An inbound group-text string has no valid target.
- **What a keyless sniffer on 0x34 *can* read (cleartext):** `MType`, `DevAddr`
  (locally-assigned, not a stable hardware id, changes on re-join), `FCtrl`,
  `FCnt`, `FPort`, length, plus PHY metadata (RSSI/SNR/SF/freq). On **LoRaWAN
  1.0.x specifically, piggybacked `FOpts` MAC commands are also cleartext**
  (encrypted only in 1.1) — but those are network housekeeping, **not**
  application text. `DevEUI`/`JoinEUI` appear in clear only during the OTAA
  Join-Request.

(Sync-word confirmation: **0x34 is the LoRaWAN public sync word** on SX127x;
the SX126x programmed equivalent is `0x3444`. It is mutually distinct from
MeshCore 0x12 and Meshtastic 0x2B, so PHY-layer separation is clean — adding
0x34 RX is trivial at the radio-config layer; the difficulty is entirely above
the PHY.)

### 14.2 The honest future scope (v8.3+, NOT v8.2)
A **one-way capture/summarize tap**, analogous to the partial Reticulum capture
path: on a radio configured to LoRaWAN, decode the cleartext header and either
log it (§13 `evt=RX proto=LW devaddr=… fcnt=… fport=… rssi=…`) and/or emit a
**metadata** MC/MT text line (`"LoRaWAN: DevAddr 0x26011F8A FCnt 4213 FPort 2
SF7 -91dBm"`). This is situational awareness, explicitly **not** message
content. True content decode is possible *only* for the operator's own
provisioned devices (ABP / imported `AppSKey`) — that is "decrypt my own fleet,"
a separate optional feature, not "bridge LoRaWAN." **TX stays a permanent
log-and-drop** (`"No TX 2 LoRaWAN"`, mirroring the RNS-dest stub) — that is the
correct end state, not a placeholder.

### 14.3 The seam (Q6) — exact, fully mapped, so v8.3 is turnkey
The dispatch surface is sync-word-driven and clean. A future LoRaWAN protocol
touches (verified against this baseline):

| File | Change | Stub cost |
|------|--------|-----------|
| `BridgeConfig.h` | `PROTO_LORAWAN` enum value | 1 line |
| `BridgeConfig.cpp` | sync→proto map: `0x34 → PROTO_LORAWAN` | 1 line |
| `MeshDecoderDebug.h` | `SYNC_WORD_LORAWAN = 0x34` constant (0x34 absent elsewhere) | 1 line |
| `MeshDecoderDebug.h` | capture decoder `printLoRaWAN()` (header-only) | v8.3 |
| `MeshEncoderDebug.h` | `encodeLoRaWAN()` stub → `return false` (permanent: no content TX) | 3 lines |
| `main.cpp` `ingestAndFanout` | RX case: capture/summarize (not text-extract) | v8.3 |
| `main.cpp` `enqueueTextForDest` switch | dest case → log-and-drop (like RNS dest) | 2 lines |
| `CaptivePortal.cpp` | protocol picker entry + sync lookup + RF defaults | ~5 lines, v8.3 |
| `LoraConfigCheck.h` | no change (sync is range-checked, accepts 0x34) | 0 |

**Two-tier seam:**
- **v8.2 (zero-risk, optional — Q6):** the enum value + the `0x34` constant
  *only*. No portal entry, no dispatch case. Reserves the address space, changes
  no behavior, touches only isolated declaration files — **zero conflict** with
  the pipeline rewrite.
- **v8.3 (the real feature):** portal entry + `printLoRaWAN` capture decode +
  the summarize-to-MC/MT path + permanent TX-drop.

**Conflict note:** the QUAD-branch audit suggested "add the stub to `main`
first, then cherry-pick." That assumed the *old* `bridgePacket()` dispatch. v8.2
**rewrites** that into `ingestAndFanout`/`enqueueTextForDest`, so the few
`main.cpp` seam lines must target the **new** pipeline — which is exactly why
the seam's `main.cpp` parts are deferred to v8.3 and only the isolated
declarations are eligible for v8.2. This avoids the merge conflict entirely.

## 15. Post-bench follow-ups (DEFERRED — implement after the bench gate)

### 15.1 Fold the Meshtastic packet_id into the MT dedup key — **APPROVED by owner 2026-06-13, do after bench**
**Observed at bench (2026-06-13):** a node sending the *same text twice* within
the 60 s dedup TTL has the second copy dropped as `loop-dup`. Live evidence: an
MT node (`!3d3a87a3`) sent `"l"` three times (distinct packet_ids
`0x3BB6/3BB7/3BB9`); the bridge **received all three** (`evt=RX` each) but
bridged only the first — the 2nd/3rd hit `drop=loop-dup` on the identical hash
`0x3d5964d8`. Same effect would hit a **stationary node's repeated identical
position/telemetry** if it broadcasts more often than the TTL. (This is a narrow
v8.2 behaviour change vs v8.1's marker scheme, which bridged each repeat. RX is
unaffected — the packets are received then intentionally deduped.)

**Root cause:** `DedupCache::hash` keys on `(decoded body + srcId)`, not the
Meshtastic `packet_id`, so two genuinely-distinct messages with identical
body+sender collide.

**Fix:** fold the MT `packet_id` into the dedup key for the Meshtastic path
only: key on `(body, src, packet_id)`.

**Why it stays loop-safe** (the load-bearing claim — cite Meshtastic firmware
when implementing): Meshtastic relays and flood-replays **preserve `(src,
packet_id)`** (that is how Meshtastic's own dedup works), so an echo/replay of a
foreign packet OR of our own emission still carries the same pid → the dedup
still matches and drops it. Only *genuinely new* user messages carry a *new*
pid → distinct hash → bridged. The on-air loop-drop already proven at bench
(`hin==hout`) keeps working because the relayed echo preserves the pid we
stamped.

**Scope / touch-points:**
- `DedupCache::hash` — add a folded 32-bit `pid` argument (or an overload);
  callers pass `pid=0` where there is none.
- **Ingest** (`main.cpp ingestAndFanout`, MT branch): parse `packet_id` from
  `buf[8..11]` (already parsed nearby for `srcId`) and fold it in.
- **Emission** (`enqueueTextForDest` MT path, `enqueueReticulumForDest` MT
  fragments): record `hash(outBody, dstSrcId, emittedPid)`. This requires
  `MeshEncoderDebug::encodeMeshtasticText` to **return the random pid it
  generates** (currently internal via `esp_random()` and not exposed) — add an
  out-param. The synthetic NodeInfo path is unaffected (not dedup-recorded).
- **MeshCore / RNS:** unchanged — GRP_TXT has no per-message id on the wire, so
  `pid=0` and MC-source identical-text repeats **remain** deduped (inherent
  accepted limitation; document it as such).

**Re-verify after implementing:** (1) send identical MT text 3× from one node →
all 3 bridge (no `loop-dup`); (2) a relayed echo of a bridged packet STILL
`drop=loop-dup` (loop-safety intact); (3) a stationary node's repeated identical
position within the TTL bridges each time; (4) two different MC senders, same
text, within TTL → 2nd still deduped (unchanged MC limitation).

### 15.2 (Cosmetic, optional) decoder-dump under the log mutex
`MeshDecoderDebug::print` still uses raw `Serial.printf`, so its multi-line
hex/protobuf dump can interleave with `blogf` lines across cores (observed at
bench as occasional garble like `[_APP) payld …`). The structured `evt=` lines
are atomic and unaffected. Wrapping the decoder dump would require threading the
log mutex into the decoder header (many printfs) — low value, deferred.
