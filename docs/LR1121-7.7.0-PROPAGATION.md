## 1. How to use this document

1. A fix (or a "don't bother" negative result) is established on **CORE1121** → record it in **§5**.
2. For each sibling that needs it, follow its **conversion recipe (§6)** — the exact files to edit
   for the chosen fix path.
3. Re-validate the sibling against the **acceptance test (§7)**. Only a pass there counts as
   "converted" — the bar is identical on all three boards.
4. Update the **dashboard (§8)**.

The fix is **not yet chosen** — it is gated on the CORE1121 **fine sweep** (does RadioLib 7.7.0
complete a packet at the OEM's winning ~+20 kHz?). See `CLAUDE.md` §0.11. Until that resolves, this
doc carries all three candidate paths so whichever wins can be propagated immediately.

## 2. Shared root cause

RadioLib **7.7.0**'s LR11x0 (LR1121) **sub-GHz LoRa RX path is deficient**: at the MeshCore narrow-BW
config (**910.525 MHz / BW 62.5 / SF7 / CR4-5 / sync 0x12**) the LR1121 detects preamble
(`irq 0x10`) but does not reliably advance to header (`0x50`) / RX_DONE (`0x08`). Established on two
physically different LR1121 boards, both running RadioLib code:

- **CORE1121 (WaveShare Core1121):** RadioLib never completes a packet; **Semtech's official
  `lr11xx_driver` COMPLETED one on the same chip** (RX_DONE, CRC-OK, 149 B @ 910.545 MHz, −74 dBm).
  ⇒ the chip receives; RadioLib's LR11x0 RX path is the deficient layer. (`CLAUDE.md` §0.11.)
- **Seeed Wio-LR1121:** identical preamble-but-rarely-completes deficit; a 9-run RX-init DOE
  (`lr1121-phase1:LR1121-RX-INIT-AUDIT.md`, hypotheses refuted) **exonerated the firmware config** —
  every UM-v2.2 remedy (RSSI cal, image cal, RxBoosted, pre-standby, DCDC, per-arm preamble) was
  tried; none recovers RX.

All three projects pin **RadioLib 7.7.0**, so all three are expected to share the defect. The cause is
**not** board wiring (it reproduces on the schematic-published Core1121 and the self-contained
boards), **not** the RSSI/AGC table, **not** the RF-switch map, **not** sync/IQ/header/CRC — all
matched to the working OEM driver and bench-eliminated (§5, and `CLAUDE.md` §0.11 table).

## 4. The three fix paths

### Path A — RadioLib 7.7.0 + fixed carrier-frequency trim (~+20 kHz)
Cheapest. Command the LR1121 RX **higher** by a fixed offset because the board reference runs **low**;
CORE1121 surfaces this as `CORE1121_FREQ_OFFSET_HZ`. Portable as a config/one-line change.
- **Pro:** trivial to apply to all three; no driver work.
- **Con / open risk:** the offset is **boot-variable** on CORE1121 (`CLAUDE.md` FM4) — a *fixed* trim
  may not reliably center, and could need AFC. **A is only viable if the CORE1121 fine sweep shows
  RadioLib actually COMPLETES at the trimmed frequency** (it has reached header at +15/+30 kHz but
  never completed). Do not port A until that is proven.

### Path B — Port the LR1121 RX path to Semtech `lr11xx_driver` (keep RadioLib for SX1262)
Most robust; the proven-good path on CORE1121 (`src/oem_rx/` + vendored `lib/waveshare_lr1121/`).
- **Pro:** uses the driver that actually completes packets; isolates the LR1121 from RadioLib's RX
  defect while leaving any SX1262 radio on RadioLib.
- **Con / open risk:** heaviest. Requires an `lr11xx` HAL shim bound to each board's SPI/CS/RST/BUSY,
  reusing the existing per-project SPI mutex, plus wrapping the driver behind each project's radio
  interface. **Untested integration:** Semtech `lr11xx_driver` and RadioLib `SX126x` have never been
  **co-linked in one binary** (today they live in mutually-exclusive build envs); the first port must
  prove they coexist without HAL/symbol conflict.

### Path C — Regress / pin RadioLib to 7.4.0
Smallest config delta (change the `lib_deps` pin), but a downgrade, not a forward fix.
- **Pro:** one-line per project (two for T_LORA_DUAL — host + co-proc must match).
- **Con / open risk:** 7.7.0 was adopted for "accumulated LR11x0 fixes"; each project uses
  7.7.0-era symbols (e.g. the `LR1121Access` protected-method idiom re-exposing
  `getErrors/calibrate/clearErrors/setRssiCalibration`, `RADIOLIB_LR11X0_CALIBRATE_ALL`,
  `RADIOLIB_LR11X0_ERROR_STAT_HF_XOSC_START_ERR`). **Whether these compile unchanged against 7.4.0 is
  unverified** — needs a 7.4.0 checkout/diff before C is declared "no logic change." Also: the
  often-cited "the LilyGO OEM example proves 7.4.0 works" is **unconfirmed** — the OEM Factory
  `platformio.ini` does not pin RadioLib at all (it is unversioned), so the 7.4.0 figure asserted in
  the T_LORA_QUAD_ROUTE docs is not derivable from disk. Verify the OEM's resolved RadioLib version
  before relying on C as a control.

### 6.1 Seeed Wio-LR1121 (branch `lr1121-phase1`)
Driver `lr1121-phase1:src/WioLR1121.cpp` (begin() sub-GHz path calls `_radio->begin(freq,…,tcxo)` at
`:366-376`; read()+defensive re-arm `:495-524`). **No frequency-trim code exists yet** (grep clean).

- **Path A:** add the trim on the **RX leg only** — `_radio->setFrequency(_config.frequency + 0.020f)`
  for the LR1121 inside `WioLR1121.cpp::begin()`/`startReceive()`, **or** add a per-chip
  `_config.freqTrimMHz` in `lr1121-phase1:src/LoraRadio.h` wired only for `CHIP_LR1121`. Prefer this
  over bumping `LORA_RADIO2_FREQUENCY` in `platformio.ini`, which would also shift TX off-channel.
  ⚠️ The +20 kHz is a **CORE1121-derived starting estimate**, not measured on this module — bench it
  against R1/HackRF before trusting (the integrated-TCXO `HF_XOSC_START_ERR` makes the true offset
  uncertain).
- **Path B:** rewrite `WioLR1121.cpp/.h` to call `lr11xx_*` (reuse CORE1121's `lib/waveshare_lr1121/`
  + an `lr11xx` HAL shim on `R2_NSS/R2_RESET/R2_BUSY` sharing the existing `spiMutex`). The SX1262 R1
  stays on RadioLib untouched. RF switch is **known**: SKY13373-460LF, **DIO5 = V1, DIO6 = V2**, RX =
  {V1 hi, V2 lo}. **⚠️ Use `MODE_STBY = {0,0}` (shutdown).** Do **not** use `{1,0}` — that was the
  suspected LNA-damage state and was reverted (`WioLR1121.cpp:287` is `{0,0,0,0,0}`; `CLAUDE.md:45`).
- **Path C:** `lib_deps … @ 7.7.0` → `@ 7.4.0`. Verify `WioLR1121.cpp`'s `LR1121Access` protected
  idiom and the 2.4 GHz `LR11x0::begin(high=true)` workaround still compile.
- **Gotchas:** the README/`main.cpp:107` comment still say "Wio SX1262" (stale — R2 is the LR1121;
  trust `platformio.ini`/`src`, not the comments). Sibling working dirs
  `…\xiao esp32 wio sx1262 dual repeater` and `…- BACKUP` were **not** inspected — if you ship from
  those trees, re-confirm their RadioLib pin and `WioLR1121` version first.

### 6.2 T_LORA_DUAL (`coproc-tlora-dual`, branch `T_LORA_QUAD` @ `3b06f3c`)
Driver `coproc-tlora-dual/src/main.cpp` — uses RadioLib **directly** for both LR1121s (`radio_3`,
`radio_4`). Base copy: config in `applyCfg()` — `setFrequency` `:109`, `setTCXO(3.3)` `:126`,
`startReceive` `:127`; `begin()`+`setRfSwitchTable` `:233-236`; RX drain `:259-274`. (Route copy: the
same setters at `:152`/`:169`/`:170`, `:297-300`.)

- **Architectural win:** the host (R1/R2 SX1262) talks to R3/R4 **only via UART frames**, so **every
  fix path is co-proc-only** — `T_LORA_QUAD/src/RemoteRadio.cpp`, `LinkProtocol.h`, `UartLink`, and
  all routing code stay untouched.
- **Path A:** add the trim in `applyCfg()` before/after `setFrequency` (`setFrequency(c.frequency +
  0.020f)`), or fold an offset into the host `CfgRadio`. ⚠️ Applies to **both** LR1121s — if drift is
  per-unit, add a **per-radio** trim field. **⚠️ Verify the TCXO first:** the co-proc issues
  `setTCXO(3.3)` for both radios, copied from the OEM Factory, **whose own comment says "BAYCKRC board
  has no TCXO"** (`Factory.ino:183`). A wrong/absent TCXO reference is itself a prime drift source —
  resolve XTAL-vs-TCXO on this hardware before trusting any trim magnitude/sign.
- **Path B:** co-proc-only port — replace the RadioLib LR1121 calls in `coproc-tlora-dual/src/main.cpp`
  with `lr11xx_*`. **A written plan already exists:** `COPROC-LR1121-DRIVER-PORT.md` (in the
  `…T_LORA_QUAD_ROUTE` dir) proposes vendoring CORE1121's `lib/waveshare_lr1121/` into
  `coproc-tlora-dual/lib/lr11xx/`. Dual-radio doubles the bookkeeping (two `lr11xx` contexts, two
  DIO9 IRQs, shared SPI). Drop RadioLib from the co-proc `lib_deps` only if no RadioLib type remains.
- **Path C:** change `@ 7.7.0` → `@ 7.4.0` in **both** `coproc-tlora-dual/platformio.ini:18` **and**
  host `T_LORA_QUAD/platformio.ini:20` (keep host + co-proc on the same RadioLib). Re-compile both;
  schema-v6/quad code may use 7.7.0 API. ⚠️ The "OEM example proves 7.4.0 works" control is
  **unconfirmed** (OEM `platformio.ini` doesn't pin RadioLib) — establish the OEM's actual resolved
  version before treating C as a validated control.
- **Decide the target copy:** base `T_LORA_QUAD` (pushed) vs `T_LORA_QUAD_ROUTE` (non-blocking
  TX/CAD, unpushed). They diverge only in the TX path; the LR1121 **RX config is identical**, so a fix
  applies cleanly to both — but land it in whichever becomes the release line.

## 7. Acceptance test (identical on all three boards)

A sibling is "converted" only when it passes this — same bar everywhere, so "fixed" means one thing.

1. **Config:** 910.525 MHz / BW 62.5 / SF7 / CR 4/5 / sync 0x12, explicit header, std IQ, CRC on,
   preamble 8 (MeshCore). Put the LR1121 in **RX-only isolation** (`R2_RX_ONLY_TEST`-equivalent) so a
   co-located SX1262 races the same channel as the control.
2. **Source:** a real MeshCore transmitter on those params, **a few metres away — NOT point-blank**
   (FM3: point-blank −38 dBm trips only preamble; a weak −74 dBm packet completed — near-field /
   front-end overload is a confound). Steady traffic; LR1121 abs-max RF input is **+10 dBm** — never
   cable a strong source in.
3. **Watch the IRQ ladder:** `0x10` preamble-only = fail; `0x50` = reached header (partial); **`0x08`
   / RX_DONE / a decoded payload = PASS.** Confirm the co-located SX1262 decodes the same packets
   (proves the channel, not the chip).
4. **Pass criterion:** reliable completions of strong **and** weak packets across **multiple boots**
   (FM4: the carrier offset is boot-variable — a fix that only works on one boot is not a fix).
5. The detailed CORE1121 bench procedure (flash/erase/monitor + the fine sweep) lives in `CLAUDE.md`
   §0.11; mirror it per board.

## 9. Open cross-project questions

- **Gating:** does RadioLib 7.7.0 *complete* a packet in the CORE1121 fine sweep (~+20 kHz, ≤5 kHz
  steps)? Picks A vs B for everyone. (`CLAUDE.md` §0.11.)
- **Boot-variable offset (FM4):** if the offset wanders per boot, a fixed Path-A trim is unreliable
  on every board → favors B or AFC.
- **T_LORA_DUAL hardware:** does the T-Lora-Dual actually have a TCXO or an XTAL? `setTCXO(3.3)` is
  issued unconditionally despite the OEM "no TCXO" comment — directly affects A's trim and the drift
  hypothesis.
- **Path C reality check:** does RadioLib 7.4.0 compile each project's 7.7.0-era symbols unchanged,
  and what version does the LilyGO OEM build actually resolve to?
- **Path B integration:** can Semtech `lr11xx_driver` + RadioLib `SX126x` co-link in one binary?
  Prove on CORE1121 (or the T_LORA_DUAL co-proc, which may not even need RadioLib afterward) before
  committing.
- **Seeed module offset:** the +20 kHz trim is inherited from CORE1121, never measured on the Seeed
  Wio-LR1121 — bench it there before shipping A.
